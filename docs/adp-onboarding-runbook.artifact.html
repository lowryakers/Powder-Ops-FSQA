Powder Ops · ReadyDoc · Onboarding → RUN Powered by ADP

ADP Onboarding Runbook

Everything between "the module is built" and "a new hire lands in RUN without anyone re-typing the packet": one variable you can set today, the ADP Marketplace registration only you can do, and the first test hire. Tick as you go; the ticks save in this browser.

For Lowry Prepared 3 September 2026 Time 20 minutes today · then weeks of waiting on ADP · 30 minutes to finish

Before you start

Two switches, and they are independent. Part A is the encryption key: without it the welcome wizard does not ask for the SSN or bank details at all. Set it today and onboarding is fully usable, with the office keying the packet into RUN by hand. Parts B–E are the ADP connection, which turns that last step into a button.

What ReadyDoc shows you along the way. Settings → Integrations lists both switches — which variables are set, and whether each is on — without ever showing a value. Use it as your "did that take?" check after every Railway change.

About the ADP screens. The portal wording below comes from ADP's own published guides; ADP rearranges its portal, so a button may be labelled slightly differently from what is written here. The meaning of each step does not change. Where a screen looks nothing like the description, stop and send me a screenshot rather than guessing.

Part A

Today: the encryption key

~10 minutes · Terminal and Railway

The SSN, routing and account numbers are stored encrypted under this key and only ever shown as the last four digits. No key, no fields. Generate it once and never change it: every value stored under it becomes unreadable the moment it moves.

01 Generate the key

Open Terminal (⌘Space, type Terminal, Return) and run:

Terminal 
$ openssl rand -hex 32
3f9a1c…64 hex characters…e7b2
Expect
One line of exactly 64 letters and digits. Select it and ⌘C. Do not close the window until step 02 is done.
This is a secret. Paste it into Railway and into your password manager, nowhere else. Not a chat, not a note, not an email.

02 Set it on the ReadyDoc service in Railway

  1. Go to railway.com/dashboard → the Powder Ops project → the ReadyDoc service card.
  2. Open the Variables tab → New Variable.
  3. Name: ONBOARDING_ENC_KEY. Value: the 64 characters from step 01. Click Add.
  4. Railway offers to deploy the change. Click Deploy (or wait; it redeploys on its own within a minute).
Expect
A new deployment appears in the Deployments tab and goes Active in two to three minutes.

03 Confirm it took, then try the wizard

  1. In ReadyDoc: Settings → Integrations. The row Onboarding — sensitive fields should read connected.
  2. Office group → Onboarding → Start an onboarding. First name Test, last name Hire, your own phone. Save.
  3. Copy the welcome link it shows (it shows once). Open it on your phone.
Expect
The wizard now has a Social Security number field and a direct-deposit page. Before the key, both said the office would collect them.

Use Cancel on that row afterwards. Onboarding is now fully usable: a real hire works the wizard, the office reads the finished packet and keys it into RUN. The rest of this runbook only removes that last keying step.

Part B

Register the app on the ADP developer portal

~30 minutes · browser · then ADP's clock

RUN has no self-serve API key. The credentials come from registering ReadyDoc as a data connector app on the ADP Marketplace developer portal, under the company's own ADP account. This is the part only you can do: it needs the RUN administrator login.

04 Create a developer account

  1. Go to developers.adp.com and choose Sign in / Register.
  2. Register with lowry@powder-ops.com and the company's legal name exactly as it appears on the RUN account. Write that name down; the certificate in Part C must match it character for character.
  3. Verify the email when it arrives.
Expect
A signed-in portal with a My Apps (or Apps) area. If it instead asks you to apply for a partner programme, choose the option for building an integration for your own company — ADP calls this the Developer Self-Service path for existing clients.

05 Create the app

  1. My Apps → Create App (or Register an application).
  2. Product: RUN Powered by ADP. App type: Data Connector (an integration that exchanges data with ADP; not SSO, not a Marketplace listing for sale).
  3. APIs / scopes: tick the HR onboarding API. On the RUN catalogue it is listed under HR as Applicant Onboarding (the event is applicant-onboard.process). If a Worker or Payroll scope is also offered, leave it off; ReadyDoc does not need it.
  4. Name and description. Use the text below; it describes what the app actually does, which is what the review reads.
App description 
ReadyDoc is Powder Ops' internal food-safety and operations system.
This connector submits a completed new-hire onboarding packet (name,
address, contact details, hire date, position, pay rate, and the tax
and direct-deposit inputs the employee entered) from ReadyDoc into RUN
Powered by ADP's Applicant Onboarding, so the office does not re-key it.
One direction only: ReadyDoc writes an applicant into onboarding; it
reads nothing back and touches no payroll data. Used by Powder Ops for
its own employees only.
Expect
An app page with a status (Draft / In review / Approved) and, once approved, a Credentials area. Approval can take weeks. Tick this step when the app is submitted, not approved.

Why the description matters. Intuit rejected the QuickBooks app on relevance, not on the code, because the description did not say plainly what it did for whom. Say it plainly here.

Part C

The certificate (mutual TLS)

~20 minutes · portal, and Terminal on one route

Every call to ADP presents a client certificate that ADP itself signed. You end up with two files: a private key (yours, never shared, shown once) and a public certificate (.pem, signed by ADP). ReadyDoc needs both. Two routes; take Route 1 if the portal offers it.

06 Route 1: let the portal generate it

  1. In the developer portal, open the Certificates section (on the app page, or in the left navigation).
  2. Click Request Certificate. Fill in the fields: Organization Name is the company name exactly as registered with ADP (step 04); Common Name is the company name followed by the word MutualSSL, for example Powder Ops MutualSSL. Leave Country, State, Locality and any password blank. Click Next.
  3. The next screen shows your private key. Click Copy, paste it straight into a new entry in your password manager named ADP mutual TLS private key, then click Ok, I copied my key.
  4. Click Done, then Download the public certificate. It arrives as a .pem file. Save that file's contents into the same password-manager entry.
The private key is shown exactly once. If you close that screen without copying it, the certificate is useless and you request a new one. Nothing is lost except a few minutes; do not try to recover it.
Expect
Two blocks of text in your password manager: one starting -----BEGIN PRIVATE KEY----- (or BEGIN RSA PRIVATE KEY), one starting -----BEGIN CERTIFICATE-----. Skip step 07.

07 Route 2: generate the request yourself and upload it

Only if the portal asks you to upload a CSR instead of generating one. In Terminal, one command makes the key, the next makes the request:

Terminal 
$ cd ~/Desktop
$ openssl genrsa -out powderops_auth.key 2048
$ openssl req -new -key powderops_auth.key -out powderops_auth.csr

The second command asks questions one at a time. Answer exactly this way (Return leaves a field blank):

  • Country Name, State, Locality: press Return, leave blank
  • Organization Name: the company name exactly as registered with ADP
  • Organizational Unit: Return
  • Common Name: the company name followed by MutualSSL, e.g. Powder Ops MutualSSL
  • Email, challenge password, optional company name: Return, Return, Return
  1. In the portal's Certificates section, Upload CSR → choose powderops_auth.csr from the Desktop.
  2. ADP signs it and offers the certificate to download as a .pem. Save it beside the key.
  3. Put the contents of both files into the password-manager entry, then delete both files from the Desktop.
Expect
The same two blocks as Route 1: a private key and a certificate.
Part D

Credentials and consent

~10 minutes · after ADP approves the app

08 Copy the client ID and client secret

  1. My Apps → open the ReadyDoc app → the Credentials (or App details) area.
  2. Copy the Client ID (a long id with dashes) and the Client Secret (a long random string; it may be shown once behind a Reveal button) into the same password-manager entry.
Expect
Four secrets in the entry now: private key, certificate, client ID, client secret.

09 Give the app consent from the RUN side

ADP checks that the company has consented before it processes a single call from the app, however good the credentials are.

  1. On the app page, find the Consent URL (the Self-Service tool lists it as the Data Connector Consent URL). Copy it.
  2. Open it in a browser where you are signed in to RUN as the company administrator. It lands in ADP's Consent Manager.
  3. Read what the app is asking for, and click Allow.
Expect
Consent Manager lists the ReadyDoc app as Allowed / Active. In RUN itself this may also appear under Settings → Apps or Data Connectors.
If not
The consent page says you are not authorised: the account you are signed in with is not a RUN administrator. Consent must come from the admin account, not an employee login.
Part E

Turn it on in Railway

~10 minutes

10 Add the four variables

Railway → the ReadyDoc service → Variables → New Variable, four times. For the two PEM values, paste the whole block including the BEGIN and END lines; Railway accepts multi-line values and ReadyDoc reads them either way.

NameValue
ADP_CLIENT_IDThe client ID from step 08
ADP_CLIENT_SECRETThe client secret from step 08
ADP_CERT_PEMThe certificate block, -----BEGIN CERTIFICATE----- through -----END CERTIFICATE-----
ADP_KEY_PEMThe private-key block, BEGIN through END

Let it redeploy.

Expect
Settings → Integrations: the row ADP (RUN Powered by ADP) — onboarding hand-off reads connected with all four names ticked.
If not
A name still shows unticked: check the variable name for a typo, letter for letter. Integrations names the missing one.

Only if ADP gave you a separate test host. Some approvals come with a sandbox API address for trial calls. If yours did, add ADP_API_BASE with that address for step 11, and remove it again before the first real hire. If it did not, leave it out; the default is ADP's production API.

Part F

The first submission

~15 minutes · phone and desktop

ReadyDoc's ADP client has never been exercised against ADP, because until now there were no credentials. The first submission is a test, and the office should be ready to correct the applicant in RUN by hand if a field lands wrong.

11 Run one onboarding through to Submit to ADP

  1. If you set a sandbox ADP_API_BASE, use invented details throughout. If you did not, use a real incoming hire with the office watching: a production submission creates a real applicant in RUN.
  2. Onboarding → Start an onboarding → fill the header → copy the welcome link → the new hire (or you, on your phone) works the wizard to the end.
  3. Back in Onboarding, the row now reads completed, with the packet's sensitive fields masked to the last four. Click Submit to ADP.
Expect
The row turns Submitted to ADP with a timestamp, and within a few minutes the person appears in RUN's onboarding queue with name, address, contact, hire date and pay rate filled. The employee's I-9 completes inside ADP's own flow, which is where it belongs.
If not
The button shows an error in ADP's own words (it starts ADP 4xx:). Copy the whole message and send it to me. Which fields the approved app may send depends on the scopes ADP granted, and the mapping is finalised against exactly that message. Nothing is lost: the packet is still on screen to key in by hand.
