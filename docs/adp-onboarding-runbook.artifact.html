Powder Ops · ReadyDoc · Onboarding → RUN Powered by ADP

ADP Onboarding Runbook

Everything between "the module is built" and "a new hire lands in RUN without anyone re-typing the packet": one variable you can set today, the ADP API Central project only you can do, and the first test hire. Revised 10 September, second pass. Parts B and C are rewritten against ADP's own API Central Quick Start Guide: API Central lives at its own address, and the certificate is made entirely in the browser — no Terminal, no openssl, no Marketplace review. Tick as you go; the ticks save in this browser.

For Lowry Prepared 3 September 2026 Time about 90 minutes end to end · no waiting on ADP

Before you start

Two switches, and they are independent. Part A is the encryption key: without it the welcome wizard does not ask for the SSN or bank details at all. Set it today and onboarding is fully usable, with the office keying the packet into RUN by hand. Parts B–F are the ADP connection, which turns that last step into a button.

What ReadyDoc shows you along the way. Settings → Integrations lists both switches — which variables are set, and whether each is on — without ever showing a value. Use it as your "did that take?" check after every Railway change.

About the ADP screens. The portal wording below comes from ADP's own published guides; ADP rearranges its portal, so a button may be labelled slightly differently from what is written here. The meaning of each step does not change. Where a screen looks nothing like the description, stop and send me a screenshot rather than guessing.

Part A

Today: the encryption key

~10 minutes · Terminal and Railway

The SSN, routing and account numbers are stored encrypted under this key and only ever shown as the last four digits. No key, no fields. Generate it once and never change it: every value stored under it becomes unreadable the moment it moves.

01 Generate the key

Open Terminal (⌘Space, type Terminal, Return) and run:

Terminal 
$ openssl rand -hex 32
3f9a1c…64 hex characters…e7b2
Expect
One line of exactly 64 letters and digits. Select it and ⌘C. Do not close the window until step 02 is done.
This is a secret. Paste it into Railway and into your password manager, nowhere else. Not a chat, not a note, not an email.

02 Set it on the ReadyDoc service in Railway

  1. Go to railway.com/dashboard → the Powder Ops project → the ReadyDoc service card.
  2. Open the Variables tab → New Variable.
  3. Name: ONBOARDING_ENC_KEY. Value: the 64 characters from step 01. Click Add.
  4. Railway offers to deploy the change. Click Deploy (or wait; it redeploys on its own within a minute).
Expect
A new deployment appears in the Deployments tab and goes Active in two to three minutes.

03 Confirm it took, then try the wizard

  1. In ReadyDoc: Settings → Integrations. The row Onboarding — sensitive fields should read connected.
  2. Office group → Onboarding → Start an onboarding. First name Test, last name Hire, your own phone. Save.
  3. Copy the welcome link it shows (it shows once). Open it on your phone.
Expect
The wizard now has a Social Security number field marked required and a direct-deposit page asking for the routing and account numbers. Before the key, both said the office would collect them. Walk it to the end: the W-4 and the I-9 each end in a typed signature, the I-9 takes photos of the ID documents, and Finish refuses until every required line and both signatures are in.

Back in Onboarding, the row reads Ready for review: the signed W-4 and I-9, the photos, and an I-9 Section 2 block for you to record the documents you examined and sign with your password. Packet PDF prints it all with the SSN as last-four. Use Cancel on the test row afterwards. Onboarding is now fully usable: a real hire works the wizard, the office reads the finished packet and keys it into RUN. The rest of this runbook only removes that last keying step.

The packet is not yet the retained Form I-9. Electronic I-9 systems have federal rules nobody has reviewed ReadyDoc against. Until HR or counsel does, complete the official I-9 from the packet — in ADP's onboarding, which has its own I-9 flow, or on paper — and examine the original documents in person within three business days. The photos are for reference.
Part B

Create the project in ADP API Central

~20 minutes · browser · no review wait

Corrected 10 September, from ADP's own API Central Quick Start Guide. API Central has its own address — you do not reach it through developers.adp.com, which is only the documentation site. Everything below matches the screens in ADP's guide.

04 Open API Central

  1. Go to api-central.adp.com and sign in with the ADP login that administers RUN.
  2. You land on the Members page. That is normal — it is API Central's default screen.
Expect
A dark blue bar reading API Central, and a left-hand menu with four entries: Projects, Certificate, Members, Integration Services.
Do not use an incognito window for this, and if you already have, that is probably the whole problem. Signing in to ADP bounces you across three addresses — api-central.adp.com, accounts.adp.com and api.adp.com — and each hand-off needs the cookie the previous one set. Chrome blocks third-party cookies in incognito by default, so the chain breaks halfway and ADP reports it as an authentication problem when it is really a cookie problem. I told you to use incognito to get past the 431. That was the wrong fix here, and this is the right one.
If sign-in
fails at all
Every failure below is the same failure. HTTP ERROR 431, Unknown Authentication Error, and a page of raw text reading "error extracting values from session" are three faces of one thing: the browser is not carrying ADP's sign-in cookies cleanly from one of its domains to the next. Do this once, in order, in a normal window:
  1. Close every ADP tab, including any incognito windows.
  2. Delete ADP's cookies. Chrome → Settings → Privacy and security → Third-party cookies → See all site data and permissions. Search adp. Delete every adp.com entry you find. This is what actually fixes the 431, and it fixes the other two as well.
  3. Start from the top, not from a link. Type api-central.adp.com into the address bar yourself. Do not use a bookmark, a pasted link, or the back button — an ADP sign-in link that has already been used once is exactly what produces "error extracting values from session".
  4. Sign in with the RUN administrator user ID — the one that runs payroll, not an employee self-service login.
Let the sign-in finish on its own. It will move through two or three addresses; that is normal, and clicking anything mid-way breaks it again.
If that
still fails

Read this before you ring them — and note that it is not what I told you an hour ago. I said the likeliest explanation was that API Central does not support RUN, on the strength of ADP's guide being written around Workforce Now. Your API Explorer screenshot narrows that considerably. Filtered to RUN Powered by ADP®, ADP lists 25 API categories and Applicant Onboarding is one of them. So the API ReadyDoc calls is a documented RUN API, and that half is settled.

What is still open is narrower and more useful: how does a RUN client get credentials for it? API Central is one answer and it will not let you in. The Marketplace partner route is the other. Those are the two things to make ADP choose between, and you can now say plainly that you know the API exists for your product — which stops the call turning into a debate about whether what you want is possible.

The Workforce Now signals are still there in the guide — the project dialog subtitled "for ADP Workforce Now®", a Workforce-Now-only permissions chapter — but they now read as evidence about API Central's own reach, not about whether RUN has the API.

Worth sending me before you call, if it is two clicks. On that same API Explorer page, click View APIs on the Applicant Onboarding card. It should name the actual endpoint. If it reads POST /hcm/v2/applicant.onboard then ReadyDoc is already built against exactly the right call for RUN and nothing in the code needs to change. If it names something else, I would rather know now than after you have credentials.

One thing worth trying while you wait on hold, because it is a different test rather than another go. Open Safari — not Chrome — and sign in at api-central.adp.com. If Safari fails the same way, that is one more thing you have ruled out and can tell them.

An internal member has to already be a registered user on your ADP account. You need none of this to finish the runbook yourself; ignore the page and go to Projects.

05 Create the project

  1. Click Projects in the left-hand menu.
  2. Click the blue Create a project button at the top right of the Projects page.
  3. A window titled Create new project opens. Fill in Project name: ReadyDoc onboarding. Paste the description below into Project description. Click Next.
  4. The next screen is Use case selection. Choose the use case for new hire onboarding — the one whose associated APIs include POST /hcm/v2/applicant.onboard. Click Create Project.
A project cannot be deleted once created. ADP says so on that screen. Get the name right the first time: ReadyDoc onboarding.
Expect
A project card on the Projects page with a View project button. Opening it shows Credentials and APIs tabs, and under Credentials a numbered list: Step 1 generate a security certificate, Step 2 obtain an access token, Step 3 call ADP APIs.
If onboarding
is not listed
The use cases on that screen are only a starting point — ADP lists the most popular ones. Create the project against the closest use case, then on the project page use the Need more APIs link to add the New Hire Onboarding APIs. Send me a screenshot of the list if you are unsure which to pick; picking the wrong one costs nothing, since APIs are added afterwards.

Part C

The certificate (mutual TLS)

~15 minutes · browser only · no Terminal

Every call to ADP presents a client certificate that ADP itself signed. You end up with two things: a private key (yours, shown exactly once, never shared) and a signed certificate (a .pem file you download). ReadyDoc needs both. API Central does all of it in the browser — the earlier version of this runbook sent you to Terminal with openssl, and that is not needed.

06 Request the certificate

  1. In API Central, click Certificate in the left-hand menu. (The other way in: Projects → View project → Credentials → Step 1, "Generate a security certificate for your organization".)
  2. Choose Request Certificate from the drop-down.
  3. The Request new security certificate wizard opens on a Getting started page. Click Next.
Expect
A wizard with four stages listed down its left side: Getting started · Generate private key · Copy/paste private key · Generate certificate.

07 Fill in the certificate form

Every field on this form is required. Fill in all of them:

  • Name your certificate: ReadyDoc Mutual SSL
  • Organization name: already filled in and greyed out — ADP sets it from what it has on file. Leave it.
  • Organization unit name: Quality
  • Country: United States
  • State/Province name: Utah
  • Locality: the city on the ADP account
  • Business email: your work address

Click Next.

08 Save the private key — this is the one that cannot be undone

  1. The Copy/paste private key screen shows a long block starting -----BEGIN PRIVATE KEY-----. Click Copy.
  2. Paste it straight into a new entry in your password manager named ADP mutual TLS private key. Do that now, before clicking anything else.
  3. Continue through to Generate certificate.
ADP cannot store or retrieve this key for you. Their own guide says so on that screen. If you close the window without copying it, the certificate is useless and you request a new one. Nothing is lost except ten minutes — do not try to recover it.

09 Download the signed certificate

  1. On the Certificates page you now have a certificate card showing the date it was generated, the date it expires, and View and Download buttons.
  2. Click Download. You get a .pem file.
  3. Open it in TextEdit and paste its contents into the same password-manager entry, underneath the private key.
Expect
Two blocks of text in your password manager: one starting -----BEGIN PRIVATE KEY-----, one starting -----BEGIN CERTIFICATE-----.

Note the expiry date. ADP signs these for about two years. Everyone marked active on the Members page gets warning emails from 60 days out. When it expires, ReadyDoc's onboarding sends stop — put the date in a calendar now.

Part D

Credentials and consent

~10 minutes · straight after Part B · nothing to wait for

Nothing is approved or reviewed here. The project exists the moment you create it, and its credentials are on the project page from that moment.

10 Copy the client ID and client secret

  1. Projects → View project on the ReadyDoc onboarding card → the Credentials tab.
  2. You will see three numbered steps. Step 1 is the certificate you already did in Part C. Open Step 2, "Obtain an access token from ADP".
  3. Copy the Client ID (a long id with dashes) and the Client Secret (a long random string; it may sit behind a Reveal button) into the same password-manager entry.
Expect
Four secrets in the entry now: private key, certificate, client ID, client secret. Step 2 also shows a token endpoint and a cURL snippet — you do not need to run it; ReadyDoc makes that call itself.

11 Consent, only if the project asks for it

A project created under the company's own ADP account is usually consented already. If the project page shows a Consent step or a Consent URL, do it; if it shows none, tick this step and move on.

  1. On the project page, find the Consent URL. Copy it.
  2. Open it in a browser where you are signed in to RUN as the company administrator. It lands in ADP's Consent Manager.
  3. Read what the app is asking for, and click Allow.
Expect
Consent Manager lists the ReadyDoc app as Allowed / Active. In RUN itself this may also appear under Settings → Apps or Data Connectors.
If not
The consent page says you are not authorised: the account you are signed in with is not a RUN administrator. Consent must come from the admin account, not an employee login.

Worth knowing about, but do not go looking for it. API Central masks sensitive personal information — bank account and routing number, birth date, tax ID — by default on a project, and there is a settings screen where that masking is changed. ADP documents it for Workforce Now; whether it applies to a RUN project, and whether it affects data being written in as opposed to read out, is not something their guide answers. Leave it alone for now. If the first real submission lands in RUN with the name and address right but the SSN or bank details missing, this is the first place to look, and I will tell you exactly what to change when we see the result.

Part E

Turn it on in Railway

~10 minutes

12 Add the four credential variables

Railway → the ReadyDoc service → Variables → New Variable, four times. For the two PEM values, paste the whole block including the BEGIN and END lines; Railway accepts multi-line values and ReadyDoc reads them either way.

NameValue
ADP_CLIENT_IDThe client ID from step 10
ADP_CLIENT_SECRETThe client secret from step 10
ADP_CERT_PEMThe certificate block, -----BEGIN CERTIFICATE----- through -----END CERTIFICATE-----
ADP_KEY_PEMThe private-key block, BEGIN through END

Let it redeploy.

Expect
Settings → Integrations: on the row ADP (RUN Powered by ADP) — onboarding hand-off the four credential names are ticked, one name (ADP_ONBOARDING_TEMPLATE_CODE) is still unticked, and a button Read what RUN requires has appeared. The row is not "connected" yet; step 13 finishes it.
If not
A credential name still shows unticked: check the variable name for a typo, letter for letter. Integrations names the missing one.

Only if ADP gave you a separate test host. Some projects come with a sandbox API address for trial calls. If yours did, add ADP_API_BASE with that address for step 14, and remove it again before the first real hire. If it did not, leave it out; the default is ADP's production API.

13 Read the onboarding template code from RUN and add the fifth variable

RUN refuses a new hire that does not name one of its onboarding templates. The code is RUN's own, so ReadyDoc reads it from ADP rather than guessing.

  1. Settings → Integrations → the ADP row → Read what RUN requires. ReadyDoc calls ADP with the new credentials and shows what came back.
  2. Find the onboarding template codes in the answer (look for onboardingTemplateCode; each has a code and a name). Pick the one for an ordinary new hire. If there is exactly one, that is it.
  3. Railway → Variables → New Variable: ADP_ONBOARDING_TEMPLATE_CODE = that code, exactly. Let it redeploy.
Expect
The ADP row now reads connected with all five names ticked, and Submit to ADP appears on completed onboarding packets.
If not
The button shows an error starting ADP 4xx:. Copy the whole message and send it to me. A 401 means the credentials or certificate; a 403 means consent (step 11) or the project's use case; anything else I read from the text.

Two optional variables, only if the answer from RUN says they are required: ADP_PAYROLL_GROUP_CODE (RUN's payroll group for new hires) and ADP_ONBOARDING_STATUS (defaults to inprogress, which lands the person in RUN's New Hire wizard for the office to finish; leave it).

Part F

The first submission

~15 minutes · phone and desktop

ReadyDoc's ADP client has never been exercised against ADP, because until now there were no credentials. It sends ADP's Applicant Onboard V2 body (POST /hcm/v2/applicant.onboard) with the person landing in RUN's New Hire wizard as in progress. The first submission is a test, and the office should be ready to finish or correct the applicant in RUN by hand if a field lands wrong.

14 Run one onboarding through to Submit to ADP

  1. If you set a sandbox ADP_API_BASE, use invented details throughout. If you did not, use a real incoming hire with the office watching: a production submission creates a real applicant in RUN.
  2. Onboarding → Start an onboarding → fill the header → copy the welcome link → the new hire (or you, on your phone) works the wizard to the end.
  3. Back in Onboarding, the row now reads completed, with the packet's sensitive fields masked to the last four. Click Submit to ADP.
Expect
The row turns Submitted to ADP with a timestamp, and within a few minutes the person appears in RUN's New Hire wizard, in progress, with name, address, contact, hire date and pay rate filled. The office finishes the wizard there; the employee's I-9 completes inside ADP's own flow, which is where it belongs.
If not
The button shows an error in ADP's own words (it starts ADP 4xx:). Copy the whole message and send it to me. ADP names the field it did not like, and the mapping is finalised against exactly that message. Nothing is lost: the packet is still on screen to key in by hand.
