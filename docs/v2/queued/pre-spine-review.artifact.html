Form 602-01

Three decisions, one trap

1 · P/F against a written spec — not a 1–5

The V2 form has no scale. Keep it that way: a scale with no spec is an opinion, a scale with one is redundant, graders can't be calibrated without reference samples, and P/F is what an auditor can check and what releases product. The simple form: each attribute shows the spec in plain words, two buttons — Matches / Doesn't match — a note required only on a fail. Five taps for a pass.

2 · The spec is per product, and the first test writes it

No finished-goods spec exists today. Rather than an authoring project across 118 SKUs: a product tested with nothing on file has its draft spec written by that test, approved once by a QA lead, then locked and read-only. Top SKUs get specs first because they get tested first. No cutover — it's per product. The record stores the spec it was graded against, the same way an ATP record carries its limit. This shape already exists for raw materials in form-607-specs.json.

3 · The Flavor Approval adopts the same five attributes and P/F

So the organoleptic record it files stays a copy, not a mapping. A new flavour's approval drafts its spec. The texted approval page shows five P/F results plus the batch adjustment; the approver decides. "Overall" goes — it was always the approver's job. This is a second controlled document, so it's raised for Document Control, not decided here.

The trap that fires on deploy. The controlled-change gate snapshots the field list only. The deploy that introduces V2 parks both forms at V1 while the pass/fail math, the shared shape, both syncs and the client switch immediately — half the app grading V2 under a V1 form. Eight second copies of the five-key shape exist outside the shared definition; the most dangerous fails to five nulls on the public approval page. Full map in docs/v2/queued/organoleptic-v2.md.
