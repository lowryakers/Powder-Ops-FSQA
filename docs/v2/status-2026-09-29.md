## 2. Three findings the Pulse list does not have

### 2.1 The sanitation area vocabulary has TWO OWNERS, and only one of them is ever cleaned

This is the one open Pulse item that is genuinely a code gap, and it is the project's own
thesis in miniature.

- The **record form's Area picker** reads the managed list `sanitation_areas`
  (`GET /structure/lists/sanitation_areas`).
- The **72-hour rule and the record normalizer** read `SANITATION_AREAS` / `canonicalArea()`
  in `server/sanitation-areas.js`.

`structure-seed.js` fills the list *from* the canonical set, so they agree on a fresh database —
but `ensureList` is additive by design (it never removes, never revives a retired option, never
overwrites an edited label). **Anything already in that list stays in it forever**, and
`previewAreaNormalization()` reads `sanitation_records` only. It has never looked at the picker.

Proven on a fresh boot, with the five strays the 25 September capture actually photographed:

```
canonical set: 20 · options the PICKER offers: 25
  "Room 7 (72 hr) cleanning"   -> REFUSED — not a room at all
  "Room 8 (72 hr) cleanning"   -> REFUSED
  "Sanitizer Dilution"         -> REFUSED
  "Simple Green"               -> REFUSED
  "Simple green"               -> REFUSED
/sanitation/areas/preview  changes: 0 · unmatched: 0
```

So the office can run **Normalize** to its end, and the form will go on offering every one of
those five tomorrow morning. That is why this has not cleared by itself.

### 2.2 The normalizer cannot fold the plant's actual spelling

`RULE_SUFFIX` in `sanitation-areas.js` anchors the "(72 hr …)" parenthetical to **end of
string**. The plant's dominant form puts the word *after* the bracket:

```
"Room 7 (72 HR cleaning)"            -> 7            ✓ folds
"Batching room 2 (72 Hr cleanning)"  -> Batching 2   ✓ folds
"Room 7 (72 hr) cleanning"           -> REFUSED      ✗  ← what the picker shows
"Room 8 (72 hr) cleanning"           -> REFUSED      ✗
```

Every record filed under the refused form stays outside the canonical set, so `recleanRooms()`
cannot join it to Room 7's production use — which is the exact failure `sanitation-areas.js` was
written to end. The module's own header even quotes this family of spellings; the regex just
does not reach the one with a trailing word.

**Fix shape (not yet built):** widen `RULE_SUFFIX` to allow a trailing *cleaning/cleanning* word
only — never arbitrary text, because arbitrary text after a room name could be a different room
— and add a **reconciliation report** that names picker options the canonical set does not
contain. Report and retire on a person's click; never auto-delete, because an option somebody
added deliberately is a decision, and options here are retired, never removed.

## 3. Single Spine: where it actually stands

**The thesis is holding.** "Give a fact exactly one owner" has produced working consolidations
well past the five CLAUDE.md names: the QMS spine, QA Review, the form registry, derived
readiness, `pm-completion`, and since then `check-forms`/`check-records` (D-060 — six programs
now file through one interface), `recordAreaForTask()`, `writeScheduleItems()` (D-102),
`scheduleAssignee()` (D-094), `decide()` (D-107), `fileAnnualReview()` (D-115),
`readybot-recipients` (D-086), `revokeSessions` (D-072), `person-links` triggers (D-074),
`AtpSwabField` (D-116). Adding a program to most of these is now one entry plus one branch.

**But the failure mode has moved, and that is the finding that should shape the roadmap.**

It used to be *two writers of one fact* — the knife mirror, the badge disagreeing with its
queue, QA records that never filed. Those are largely closed.

What the last twenty decisions actually keep finding is different:

> **The mechanism exists, is correct, is tested — and is reachable from nowhere the person who
> needs it will ever look.**

D-079 (the 30/90-day checks: *"the machinery existed and nobody found it"*) · D-097 (*"the
arithmetic already existed"*) · D-101 (the inventory editor only on a screen Document Control
cannot open) · D-103 (`training_requirements` read by the matrix, written by nothing;
`sop_id` wired to nothing on all courses) · D-104 (`zoneDrift` reporting to a deploy log) ·
D-105 (assignments reaching nobody) · D-110 (the link field with no box) · D-111 (the recall
chart only in the binder) · D-112 and D-116 (the ATP box, on two screens).

**Eleven of the last twenty.** The spine is being built faster than it is being surfaced. The
same is true one level up: D-010's three repair paths are built and have never been run, and
the obligations register cannot show the software that shipped.

So the next unit of work is not another consolidation. It is **reachability**.
